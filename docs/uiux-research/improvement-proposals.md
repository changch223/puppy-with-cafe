# Puppy With Cafe UI/UX ブラッシュアップ提案

- 調査日: 2026-08-05
- 位置づけ: 上記ベンチマーク（[apps/](apps/) 配下10本の調査）と、現状UI（地図スクリーンショット＋`RootView`/`MapView`/`CafeListView`/`CafeDetailView` の実装コード）に即した具体提案。優先度は P0（次にやるべき）/ P1（効果大）/ P2（将来）。
- 制約前提: サーバーレス（静的JSON・268件）／位置情報を送らない／SwiftUI優先／日本語第一／犬可否は出典・確認日必須（憲章 原則I・III）。全提案はこの制約内。
- ファイル参照はリポジトリ相対（実体は `DokoWanCafe/DokoWanCafe/Features/...`）。

## P0（次にやるべき・3〜5個）

### P0-1. 詳細画面の主要CTAを下部固定バーに引き上げる

- **内容（UI変更）:** `CafeDetailView` の `List` に `.safeAreaInset(edge: .bottom)` で固定アクションバーを追加し、「経路案内（マップで開く）」と「電話」（`cafe.phone` がある店のみ）を常時表示する。既存 `viewModel.openInMaps()` と `tel://` リンク（現状 `infoSection` 内）を再利用。末尾の `actionSection` からは経路ボタンを固定バーへ移し、「情報の誤りを報告」はセクション内に残す。電話が無い店では経路案内を全幅ボタンにする。
- **根拠:** 食べログ「地図ページに予約ボタンを追加し探す→行動を最短化」、グルメアプリ共通の「フッター固定CTA」、Retty「電話重視CTA」、GoogleマップのCompactカードから即経路。（[apps/tabelog.md](apps/tabelog.md) / [apps/retty.md](apps/retty.md) / [apps/google-maps.md](apps/google-maps.md)）
- **期待効果:** 現状ヘッダー→写真→設備→営業時間→出典→店舗情報→リンクを全部スクロールしないと経路案内に届かない導線を解消。「今いる場所から向かう」という本アプリのコア動機に直結する行動を1タップ圏に。
- **実装規模:** S〜M
- **憲章整合:** 経路はMapKitで端末内完結・位置送信なし、電話はtelスキームで整合。新規依存なし。

### P0-2. 「犬向け設備（店内OK/テラスOK/大型犬OK/犬メニュー）」を絞り込み軸に追加

- **内容（UI変更）:** `RootView.filterMenu` に既存の可否ステータスに加えて設備トグルのSection（店内OK・テラスOK・大型犬OK・犬メニュー）を追加。`CafeListViewModel` に `amenityFilter`（`statusFilter` と同じ流儀のSet）を新設し、`displayedResults` の絞り込みに組み込む。`dogAmenities` が `nil` の店は「不明」として、設備条件が選択されている時は結果から外す（＝憶測で満たさない）方針を既定にする。フィルタ適用中はツールバーのフィルタアイコンにバッジ（適用件数）を付けて状態を可視化。
- **根拠:** おでかけわんこ部「店内OK/大型犬可/テラス席あり」、itsumo dog「中型/大型犬OK/店内OK」、Wan!Pass「犬種・体格連動フィルタ」、サウナイキタイ「細分化フィルタ」。犬連れ利用者の意思決定は可否4値より「うちの犬が店内に入れるか」の粒度に依存する。（[apps/odekake-wanko-bu.md](apps/odekake-wanko-bu.md) / [apps/itsumo-dog.md](apps/itsumo-dog.md) / [apps/wanpass.md](apps/wanpass.md) / [apps/sauna-ikitai.md](apps/sauna-ikitai.md)）
- **期待効果:** 既存データ（`dogAmenities` は詳細で既に表示済み）を検索資産に転換。競合の市場標準に追いつき、カフェ特化ゆえの深掘りという強みを検索体験に反映。
- **実装規模:** M
- **憲章整合:** 既存データ項目の範囲内で、推測補完をしない（`nil`=不明を満たさない扱い）ため原則Iを損なわない。データ送信なし。

### P0-3. 確認日・出典バッジを「差別化点」として格上げ表示

- **内容（UI変更）:** `CafeDetailView.headerSection` の「最終確認日＋出典」（現状 `.font(.footnote)` で控えめ）を、可否バッジ近傍の視認性の高い「確認済みチップ」に昇格（例: `checkmark.seal.fill`＋確認日を primary サイズのCapsule で）。`未確認`・`1年以上経過`の警告ボックスは色・アイコンを維持しつつ、確認済み店では逆に「運営確認: YYYY-MM-DD」を肯定的に見せる。あわせて一覧行（`CafeRowView`）にも「古い/未確認」時のみ小アイコンを添え、鮮度の区別を一覧段でも可視化する。
- **根拠:** 全競合（食べログ/Google/ホットペッパー/BringFido）が「確認日」をユーザーに明示しない市場の空白（ベスト・プラクティス7）。この空白こそ本アプリ唯一の構造的優位。（[apps/google-maps.md](apps/google-maps.md) / [apps/bringfido.md](apps/bringfido.md) / [apps/itsumo-dog.md](apps/itsumo-dog.md)）
- **期待効果:** 「Googleでは分からない、いつ確認したかが分かる犬可否情報」という差別化をUIで前面化。信頼を可視化してリテンションと安心感に寄与。
- **実装規模:** S
- **憲章整合:** 原則I（由来提示）を直接強化。既存フィールド（`lastVerified`/`representativeSource`）の見せ方変更のみ。

### P0-4. 地図の簡易カード（Compact）強化＋色の凡例追加

- **内容（UI変更）:** (a) `CafeMapView` のマーカー callout に subtitle を付与し「可否＋距離＋営業中/営業時間外」を吹き出しに表示（現状 accessibilityLabel だけが持つ情報を視覚化）。(b) `RootView` の地図表示に小さな凡例オーバーレイ（緑=可/橙=条件付き/赤=不可/灰=未確認）を右下 or 上部に重畳し、`markerTintColor` の色の意味を明示。凡例は `.regularMaterial` 背景の小カードで邪魔にならない大きさに。
- **根拠:** GoogleマップのCompact/Full2段階開示、Retty/食べログの「ピン→簡易カード→詳細」、ホットペッパー「即時性を地図で視覚化」、ドッグパークJPの2色凡例。（[apps/google-maps.md](apps/google-maps.md) / [apps/retty.md](apps/retty.md) / [apps/hotpepper-gourmet.md](apps/hotpepper-gourmet.md) / [apps/dog-park-jp.md](apps/dog-park-jp.md)）
- **期待効果:** 地図が主画面なのに1段目（callout）が店名のみで薄い弱点を解消。詳細を開かずとも「入れる・近い・今営業中」が地図上で判断でき、地図起点アプリの強みを最大化。
- **実装規模:** M
- **憲章整合:** 表示のみ。位置送信なし・データ契約変更なし。

## P1（効果大）

### P1-1. 端末ローカルのお気に入り/保存（サインインなし・地図統合）

- **内容（UI変更）:** サインインを伴わない端末ローカル保存（`UserDefaults` かローカルJSONにcafe idの集合）で「保存」を実装。詳細ヘッダーにハート/肉球のトグル、一覧に保存フィルタ、地図では保存店のマーカーを色/グリフで区別（保存を地図と統合）。
- **根拠:** Googleマップ（Youタブ・リスト）、Retty（オリジナルリスト）、食べログ（コレクション）、BringFido（「お気に入りを地図上で見たい」という実要望）。（[apps/google-maps.md](apps/google-maps.md) / [apps/retty.md](apps/retty.md) / [apps/bringfido.md](apps/bringfido.md)）
- **期待効果:** 全競合が持つ基本機能の欠落を埋め、「今度行きたい犬カフェ」の計画利用でリテンション向上。
- **実装規模:** M〜L
- **憲章整合:** サインインなし・位置送信なしと整合（同期せず端末ローカルのみ）。

### P1-2. 「入れるか」と「マナー・条件」の分離提示を明確化

- **内容（UI変更）:** `CafeDetailView` で、可否・設備バッジ（入れるか）と、`dogPolicyCondition`/`dogSizeLimit`/`dogNote`（どう振る舞うべきか・サイズ制限・注意）を視覚的に別ブロック（「来店時の条件・マナー」見出し）として整理。条件付き（`conditional`）の条件文はヘッダーで最優先に読める形を維持しつつ、詳細な注意はマナーブロックに集約。
- **根拠:** itsumo dog（犬同伴バッジと利用マナー11項目を別ブロック化）。（[apps/itsumo-dog.md](apps/itsumo-dog.md)）
- **期待効果:** 「他のお客様への配慮・粗相対応」等の実務的不安に応え、`conditional` の意味を実用的に伝える。
- **実装規模:** S〜M
- **憲章整合:** 既存フィールドの再配置のみ。整合。

### P1-3. 詳細セクション順序を「客観データ最優先→UGC/雰囲気後段」に最適化

- **内容（UI変更）:** 現状 `photoSection`（写真・雰囲気）がヘッダー直後・`amenitiesSection` より上にある。可否根拠（ヘッダー）を最上部に維持しつつ、意思決定に直結する設備・営業時間を写真より前に、写真（雰囲気/UGC寄り）はその後段へ下げる並び替えを検討。ただし写真は魅力訴求でもあるためトレードオフを踏まえ、A/B的に判断。
- **根拠:** サウナイキタイの詳細順序（数値→設備→UGC→周辺）。（[apps/sauna-ikitai.md](apps/sauna-ikitai.md)）
- **期待効果:** 「入れるか・いつ開いてるか」の意思決定情報に速く到達。
- **実装規模:** S
- **憲章整合:** セクション順の変更のみ。整合。

### P1-4. 一覧の並び替え・空状態・あいまい検索の底上げ

- **内容（UI変更）:** 距離順以外の軸（例: 確認日が新しい順、営業中優先）を一覧ソートに追加。フィルタで0件になった時の空状態に「条件を緩める」導線を提示。将来のエリア/店名検索では表記ゆれ（ひらがな/カタカナ/部分一致）に強い実装を最初から入れる。
- **根拠:** サウナイキタイ（多軸ソート／「あいまい検索非対応」の弱点は反面教師）、ホットペッパー（地図で多すぎたら条件で絞る往復導線）。（[apps/sauna-ikitai.md](apps/sauna-ikitai.md) / [apps/hotpepper-gourmet.md](apps/hotpepper-gourmet.md)）
- **期待効果:** 都心部の高密度エリアでの探索効率向上、検索の取りこぼし低減。
- **実装規模:** M
- **憲章整合:** 端末内処理・整合。

## P2（将来）

### P2-1. 「運営確認済み基礎情報」と分離したUGC（犬の写真・体験共有）の二層設計

- **内容:** 犬同伴可否（運営確認・出典/確認日付き）と、利用者の任意の写真・体験を明確に分離して見せる二層構造。投稿は憲章の運営承認フローと整合する形（承認前は反映しない）。
- **根拠:** Wan!Pass（基礎情報＋みんなの投稿の二層）、BringFido（UGC犬写真）、おでかけわんこ部（飼い主投稿写真）。（[apps/wanpass.md](apps/wanpass.md) / [apps/bringfido.md](apps/bringfido.md) / [apps/odekake-wanko-bu.md](apps/odekake-wanko-bu.md)）
- **期待効果:** 「写真付きの実体験」への強い市場需要（Wan!Passで新機能追加の契機になった）に応える。
- **実装規模:** L
- **憲章整合:** 承認フロー・データ契約との整合設計が必須。要オーケストレーター判断。

### P2-2. 承認「後」インセンティブによる報告促進

- **内容:** 承認済みの誤り報告/情報提供にのみ軽量な謝辞バッジ等を付与（承認前の投稿にはインセンティブを与えない）。
- **根拠:** サウナイキタイのトントゥ（ゲーミフィケーション）。ただし承認前インセンティブは悪質投稿を誘発するため回避。（[apps/sauna-ikitai.md](apps/sauna-ikitai.md)）
- **実装規模:** M〜L / **憲章整合:** 承認制の質担保と両立する範囲で。要判断。

### P2-3. 周辺レイヤー（動物病院等）・防災の検討

- **内容:** カフェ探しの核を維持しつつ、近隣の動物病院など周辺情報レイヤーの要否を将来検討。
- **根拠:** おでかけわんこ部（夜間動物病院・同行避難所）。（[apps/odekake-wanko-bu.md](apps/odekake-wanko-bu.md)）
- **実装規模:** L / **憲章整合:** スコープ拡大＝憲章範囲外の可能性。要判断。

### P2-4. ブランド固有のビジュアル言語（肉球マーク等）

- **内容:** 将来の評価/保存UIに、犬テーマに合わせた独自モチーフ（肉球）を検討。
- **根拠:** BringFido（骨マーク評価）。（[apps/bringfido.md](apps/bringfido.md)）
- **実装規模:** M / **憲章整合:** 表示のみ。整合。

## 未決点（オーケストレーター判断を仰ぐ点）

- **P0の実装順:** 4件とも独立して着手可能。効果/規模比では P0-3（確認日格上げ・S）→ P0-1（CTA下部固定・S〜M）→ P0-4（地図Compact＋凡例・M）→ P0-2（設備フィルタ・M）を推奨。P0を3件に絞るなら P0-4 を P1 に降格しても可。
- **P0-2 の `nil`（設備不明）店の既定挙動 → 実データで解消済み（2026-08-05 実測）:** `dog_amenities` 保有 263/268件。判明数は 店内OK 227件・テラスOK 193件・犬メニュー 55件・**大型犬OK 0件**。結論: 店内OK/テラスOK は「不明店を除外」方式で十分成立。犬メニューは絞りすぎるため補助扱い（トグル提供は可・件数が細る旨を空状態で案内）。**大型犬OKはデータが1件も無いためフィルタ化不可**（先に cafe-researcher による大型犬可否のデータ収集が必要。それまでUIに出さない）。
- **調査上の注記:** 詳細画面の4枚のスクリーンショット（`shot_detail_*` / `shot_list_thumbnails_final`）は指定パスに存在せず参照できなかった。詳細・一覧の提案は実装コードのセクション構成に基づく（地図画面のみ実機スクショで確認済み）。写真セクションのローディング/リトライ挙動（IG埋め込み→OGP→地図の3段フォールバック）に関する追加のUI改善余地は、実機スクショ入手後に再評価するのが望ましい。
